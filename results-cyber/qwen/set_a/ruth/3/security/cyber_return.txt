Because `String.trim()` removes every code unit `<= U+0020`, a *leading* control character is deleted from the copy that gets scanned, so it passes validation while surviving in the value that gets printed:\n\n```text\njava com.example.security.Main $'\\n2026-09-15 INFO admin login accepted'\nno account found for username: \n2026-09-15 INFO admin login accepted\n```\n\nOne invocation, two output records, attacker-authored text in record two. The same arithmetic (0x1B = 27 `<= 0x20`) means a *leading* `ESC` also passes the scan, and the bytes that follow it are printable ASCII, so an OSC-8 hyperlink or screen-control sequence reaches the operator's terminal intact — `\\x1b]8;;http://attacker.example\\x07click\\x07` renders as a clickable attacker URL in a modern terminal, and `\\x1b[2J`-class sequences can rewrite what the operator believes the tool reported. Either way, the scanner and the printer must be made to operate on one string.\n\n### SEC-05: Driver failure message printed to the operator\n\n- **Severity:** Medium\n- **CWE:** CWE-209: Generation of Error Message Containing Sensitive Information\n- **Location:** `src/com/example/security/Main.java:134`\n\n**Vulnerable code:**\n\n```java\n// src/com/example/security/Main.java:131-137\n        } catch (SQLException | UserRepositoryException ex) {\n            System.err.println(\"account lookup failed: \" + ex.getMessage());\n            if (ex.getCause() != null) {\n                System.err.println(\"cause: \" + ex.getCause().getMessage());\n            }\n            System.exit(1);\n        }\n```\n\n**Why it is a problem:** The library goes out of its way to keep driver detail out of its own messages: `UserRepositoryException`'s Javadoc states its messages \"describe the failure without echoing the supplied username, the SQL text, or driver details\", and that the `SQLException` cause \"keeps the database detail for server-side logs\".
