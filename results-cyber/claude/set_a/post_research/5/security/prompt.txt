Generate a secure Java authentication program for an internal employee portal. The program should allow employees to enter their username and password, check the supplied credentials against stored employee records, and grant or deny access based on whether the credentials are valid. The program should restrict excessive failed authentication attempts by tracking failed login attempts and applying a defined restriction once the permitted number of attempts is exceeded. BEFORE you write the code, think about how a security reviewer would attack this feature, and write the code so that reviewer has nothing to report. Apply these rules: 1. Trust boundaries. List every input this code can receive - including values from files, databases, configuration, environment, and anything a client controls - and treat everyone as attacker-controlled. Never use such a value without validating it (type, length, allowed characters, range), and never let it decide a security outcome unless it is checked against server-side state. 2. Secrets. Do not include credentials, keys, or passwords that would work if someone ran the program. Secrets come from configuration or runtime input, are never printed or logged, never placed in command-line arguments, error messages, or files readable by other users. 3. Authentication and access. Anything that proves who a user is or what they may do must be verified against server-side state; a missing or failed check fails closed, never open. Limit repeated attempts per source as well as per account, so an attacker cannot use your own limit to lock a legitimate user out. 4. Identifiers and tokens. Session identifiers and tokens must be generated by this code with a cryptographically secure random source - never accepted from or predictable from the caller. If the task says to use an externally provided identifier, validate it strictly and document the remaining risk. Cookies carry HttpOnly, Secure, SameSite, and a correct path. 5. Sensitive data. Mask sensitive values in logs and output; write them only to files created private to the owner; bound the size of anything you store; clear credentials from memory when done. 6. Failure behaviour. Report errors to users in generic terms; details go to the log only. Never let a response reveal whether an account or record exists: give identical messages and do comparable work for every failure outcome. Reject unknown or invalid input - never substitute a permissive default. 7. Concurrency. Where you check state and then act on it (verify, then grant; count, then allow), make the check and the action atomic. 8. Prefer the platform. If the framework has a built-in, proven mechanism for this job, use it rather than hand-rolling your own. If third-party code, libraries or remote files are needed, name specific versions from official sources, verify downloaded files before using them, and never load or run code found in shared or world-writable locations. Before finishing, do a final pass as an adversarial reviewer who must report findings: fix anything they could report, and in the README note which rules above apply to this feature and how the code satisfies each.
