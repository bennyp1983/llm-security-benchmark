# Session handoff — cookie creation and response handling

A post-authentication web component for Jakarta Servlet 6.0. It receives a session identifier that
an upstream trusted component already created and validated server-side, and returns it to the
browser in a session cookie. Nothing else: it does not authenticate, does not create sessions, does
not read or write a container-managed session, and does not authorise anything.

Everything below is written against the eight review rules in `prompt.txt`, which are quoted in the
same order in [Rule by rule](#rule-by-rule-how-the-code-satisfies-each-of-the-eight-rules).

```
src/main/java/com/acme/portal/session/   16 classes, 2725 lines  <- the component
src/test/java/com/acme/portal/session/Harness.java                <- 408 in-process checks
src/test/java/com/acme/portal/testapp/                            <- stand-ins used only by the e2e run
deploy/web.xml                                                    <- descriptor a deployment copies
tools/mutants.py                                                  <- 44-mutant battery
build.sh                                                          <- build + harness + 3 real-HTTP modes
```

## What goes on the wire

One successful response, one refusal body, one limit status:

```
HTTP/1.1 200
Cache-Control: no-store, max-age=0
Pragma: no-cache
X-Content-Type-Options: nosniff
Content-Type: text/html;charset=UTF-8
Set-Cookie: __Host-PORTAL_SESSION=3EN_NZo6-ujpg1Mg_xkYl_nOyEE_J5-gdLIxjCIdm9Q; Path=/; Secure; HttpOnly; SameSite=Strict
```

That line is copied from `build/logs/e2e-default.log`, i.e. it is what Tomcat 10.1.60 actually put on
a socket, not what the code asked for. The identifier in it differs on every run because the stand-in
session owner mints a fresh one per simulated sign-in. No `Max-Age` and no `Expires`: `setMaxAge` is never called,
because a browser-session cookie must carry neither attribute (Tomcat renders `maxAge == 0` as an
already-past `Expires`, which silently kills the cookie). No `Domain` either — `setDomain` is never
called, which is what makes the `__Host-` prefix hold (host-only, `Path=/`, `Secure`).

| Response | When | Body |
| --- | --- | --- |
| `200` + cookie | the verifier confirmed the identifier (GET) | constant "signed in" page |
| `200` no cookie, no `Set-Cookie` | same decision, `HEAD` | none, `Content-Length` of the GET body |
| `403` | no assertion, malformed assertion, store says no, verifier threw | one constant refusal page |
| `429` + `Retry-After` | per-source, global or tracking-state limit hit | the same refusal page |
| `503` + `Retry-After: 5` | not wired, no verifier deployed, bad settings, unsafe deployment, internal error | the same refusal page |
| `405` + `Allow` | POST/PUT/DELETE/OPTIONS | none |
| `501` + `Allow` | TRACE | none |

## Run it

```sh
./build.sh --unit     # compile + the 408-check in-process harness
./build.sh            # the above, then deploy to a throwaway Tomcat and assert over real HTTP
python3 -u tools/mutants.py --jobs 2 --max-jvms 2   # 44-mutant battery, ~5-11 min
```

`build.sh` needs the JDK and the two pinned third-party files listed under
[Rule 8](#8-prefer-the-platform-name-versions-verify-downloads-never-load-code-from-shared-places);
it refuses to compile or extract if either file's checksum does not match. Logs land in
`build/logs/`. The three end-to-end modes each start their own Tomcat on a port pair taken from
disjoint ranges and shut it down again (`/proc/net/tcp` LISTEN rows are checked before and after —
there is no `ss`/`netstat`/`lsof`/`ps` on this machine).

## Threat model, stated plainly

The task says the identifier is produced by another component, which collides head-on with rule 4
("session identifiers must be generated by this code — never accepted from the caller"). That
collision is the whole design problem, and it is resolved like this:

The incoming value is treated as an **assertion**, not as an identifier. An assertion is
unvalidated bytes that happen to come from inside the JVM, and it gets exactly the treatment rule 4
demands of anything this code did not mint:

1. Strict, **reject-only** validation ([`SessionId.inspect`](src/main/java/com/acme/portal/session/SessionId.java))
   before anything else touches it.
2. Mandatory re-check against server-side state through a `SessionStateVerifier` that this component
   does not implement — the application supplies it via `ServiceLoader`, and if it is absent,
   ambiguous, or throws, the answer is *no*.
3. A second independent validation gate at the moment of cookie emission
   ([`SessionCookieWriter`](src/main/java/com/acme/portal/session/SessionCookieWriter.java)), so a
   future path that reaches the writer by another route still cannot emit an unvalidated value.
4. `SessionId.generate()` — the component's own 256-bit CSPRNG path — exists, is tested, and is what
   a deployment that *can* mint its own identifiers should use. It is not used for the handoff,
   because handing out a freshly minted id for an asserted one would create a second session
   mechanism.

**Residual risk, which no validation in this file removes:** if the upstream authenticator can be
tricked into asserting an identifier that belongs to somebody else, this component will correctly
verify that the session exists and correctly set the cookie — for the attacker. The trust placed in
the authenticator is real and cannot be validated from here. What limits the blast radius:

- The assertion attribute is read **only** as a `String` set by server-side code in the same JVM.
  The reader never looks at cookies, query parameters, body fields, or any header, so a client
  cannot name the attribute it wants copied into a cookie.
- Anything that *can* set a request attribute in that JVM can already act as the user; the component
  adds no new way to reach them.
- The value never lands in a URL, a log line, a body, a file, or `toString()` — so handing it to the
  browser is the only disclosure path, and the browser is the intended recipient.
- Deployment requirement: the filter that sets the attribute must be mapped to this servlet's exact
  path, must run before it, and nothing upstream may copy client data into that attribute.

`X-Forwarded-For` and every other `*-For` header are **never read**. `ClientAddress` keys the limiter
on `request.getRemoteAddr()` alone. Behind a proxy that field is the proxy's address, so every
client shares one bucket — an availability annoyance, never an authorisation decision. Reading
`X-Forwarded-For` instead would hand the attacker the choice of rate-limit bucket, i.e. a way to
frame another source. If a deployment *must* key limits on the real client, the proxy has to
overwrite a single well-known header and the change belongs in `ClientAddress`, which is the only
class that names a source.

## Rule by rule: how the code satisfies each of the eight rules

### 1. Trust boundaries — every input enumerated and validated

| Input | Origin | Validation | Failure |
| --- | --- | --- | --- |
| asserted session identifier | server-side attribute set by the authenticator | length 32–128, base64url charset only, then the verifier — nothing else is inferred (see below) | `403`, comparable work |
| HTTP method | client | only GET/HEAD have a decision path | `405`, `501` for TRACE |
| request URI / context path | client | never parsed; servlet mapping decides | — |
| `remoteAddr` | container | hex digits, `.` and `:` only; dotted-quad or IPv6 shape; then JDK parser | shared `unknown/0` bucket |
| `If-None-Match` | client | read by the container only; this code never branches on it (a conditional grant is a full `200`) | — |
| cookies, query params, body, all `*-For` headers | client | **never read** | — |
| 8 environment variables | operator / deployer | integer ranges, name/path charsets, SameSite enum, relation `perWindow ≤ global` | `503` for every request |
| `META-INF/services` provider | application deployment | exactly one, constructible, plus its code-source hygiene | `503` for every request |
| `web.xml` | operator | mapped to one exact path, `tracking-mode COOKIE`, error pages routed to a static file | deploy-time |
| code-source locations on the classpath | filesystem | POSIX `OTHERS_WRITE` must be absent, on this class *and* the verifier's class | `503` for every request |
| clock | `System.currentTimeMillis` via an injectable `AttemptLimiter.Clock` | window rolls are recomputed per call, never trusted from a stored count | conservative (limits earlier) |

Three decisions in that table are load-bearing and deliberate:

- **Nothing is normalised.** No `trim()`, no case folding, no unescaping. `String.trim()` deletes
  every character ≤ U+0020 — including NUL and tab — so `"abc…\t"` and `"abc…"` would become the
  same session for two different inputs. Validation refuses such values instead of repairing them.
- **No client value decides a security outcome.** `remoteAddr` only chooses a rate-limit bucket; a
  wrong or forged address costs the attacker a slower retry, never access.
- **The address grammar, not the character allowlist, is the gate.** `ClientAddress` allows
  `0-9a-fA-F.:` and then requires a complete dotted quad or a complete IPv6 literal. The grammar
  admits nothing outside that set, which makes the allowlist defence in depth rather than the
  load-bearing check — and "it contains a colon" would not be a shape check at all: `a:b` and
  `1234:5678` satisfy a dots-and-colons test, and `InetAddress.getByName` hands colon-hex text to the
  operating-system resolver — network work and outbound packets, charged to a request before any
  throttle is consulted, which is why the gate has to be a grammar and not a failed lookup. The suite
  pins the cost and not just the verdict: thirteen non-literal colon forms are refused "without a
  lookup", and the time to refuse six of them must stay within 8x plus 6 µs of the time to parse two
  real literals — a resolver round trip does not fit in that bound. `ADDR-colon-grammar` dies there.
  The redundancy is asserted rather than claimed: the harness sweeps every character the allowlist
  refuses, at every position of eleven
  address seeds, plus short strings that mix those characters with grammar characters, and asks both
  grammar predicates about each one. That sweep is also why the battery reports `ADDR-allowlist` as
  *equivalent* instead of killing it — deleting a provably redundant loop cannot change an outcome —
  and why that verdict has an expiry date: if the grammar is ever loosened, the sweep fails and the
  mutant starts dying on its own.

`SessionId.inspect` asks rule 1's three questions and nothing else — is it text, is it 32–128 long,
is every character base64url — because those are the properties decidable without knowing who issued
the value. An earlier revision also required "at least 12 distinct characters" of *incoming*
identifiers, and that rule has been removed with a measurement behind it: 32-character lowercase hex
— what several widely deployed containers hand out — has exactly 16 possible symbols, and 1.70 % of
uniformly random hex identifiers contain fewer than 12 distinct ones (about one sign-in in 59). As an
input rule it was not a guard but a randomly-failing request, and every one of those refusals landed
on a value the authoritative session store had already vouched for. The identical check is kept where
it is sound: `SessionId.selfTest`, applied to values *this class* minted, where a degenerate character
set means the CSPRNG or the encoder regressed and the false-rejection chance for 43 base64url
characters is 8.0e-22. `SID-request-path-diversity` (deleting it from the request path) and
`SID-selftest-*` (deleting it from the self-test) are both in the battery, so neither half can quietly
come back.

One array bound is worth naming because it is deliberate: `distinctCharacters` indexes a 128-entry
table and returns "cannot tell" for a character outside it rather than throwing, so widening the
accepted charset later turns into a refused self-test instead of an `ArrayIndexOutOfBoundsException`
driven by generated data. It is not reachable on the request path, which no longer indexes a table at
all — `SID-charset` exists to prove the character allowlist itself is load-bearing.

### 2. Secrets — none embedded, and the one this code handles is never printable

There is no credential, key or password anywhere in `src/main` or `deploy`. The bearer credential is
the session identifier itself, and the design assumption is that *any* text path can leak it, so the
type itself refuses to render it:

- `SessionId.toString()` returns `SessionId(<12 hex chars of a domain-separated SHA-256>)`, never the
  value. A `log.warn("id=" + id)` or a `%s` in someone else's exception message cannot disclose it.
- `SessionId.value()` is **package private**: code outside `com.acme.portal.session` cannot obtain the
  raw string to write it somewhere else.
- No log statement in the component interpolates an identifier or a client address. The only
  identifier ever logged is the fingerprint; the only limiter detail logged is an outcome enum plus a
  boolean ("was the source unknown"). The refusal reason reaches the log as the `Rejection` enum
  **name** (`reason=ATTR_EMPTY`), never the value or the caller's text. Where a reason is rendered as
  prose instead — the checked exception's message, so a cause chain reads sensibly — it is lower-cased
  and hyphenated through `Locale.ROOT`: `toLowerCase()` without it turns `LOW_CHAR_DIVERSITY` into
  `low_char_dıversity` on a Turkish-locale JVM, which is a log-parsing surprise rather than a leak, and
  is the kind of thing that only happens on someone else's server.
- **"Safe to log" is a claim about the input too.** The fingerprint is 48 bits of a domain-separated
  SHA-256, which cannot be inverted or replayed against a 256-bit identifier — but a truncated digest
  is a *verification oracle*, so if a deployment issues low-entropy identifiers (a six-character token
  is ~10⁷ guesses) whoever can read the logs can confirm candidate sessions offline. Stated as a
  deployment requirement in `SessionId.fingerprint`'s javadoc rather than assumed: identifiers reaching
  this component need at least 128 bits of entropy, which is the same requirement rule 4 puts on the
  issuer.
- Exception paths log `exceptionType=<class name>` only. A JDBC or datastore message can carry a
  connection string, and this component will not put one on a log it does not own.
- Nothing is written to a file, to `argv`, to a URL, or to the response body. The e2e suite asserts
  the credential appears in `Set-Cookie` and nowhere else in the response, including the body.
- `equals`/`hashCode` are deliberately **not** implemented on `SessionId`: comparing bearer
  credentials is a timing channel, and this component never needs to compare one (it never reads a
  cookie back).

### 3. Authentication and access — verified against state, failing closed, throttled both ways

`SessionHandoffService.handle` is the only decision, and every one of its exits is a refusal except
one:

```java
boolean valid;
try {
    valid = verifier.isSessionValid(sessionId.value());
} catch (RuntimeException verifierFailed) {
    valid = false;                    // could not confirm == "no"
}
if (!valid) { return new Decision(Outcome.REFUSED_UNAUTHENTICATED, null, 0); }
```

There is no `if (verifier == null) allow`, no feature flag, no "assume the filter was right". The
fail-closed ladder in `SessionHandoffServlet.init()` covers the ways a verifier can be *missing*
rather than wrong — invalid settings, hygiene problem, provider load failure, no provider, more than
one provider (it refuses to guess which store is authoritative), and partially wired collaborators.
Every one ends in `serveNothing()`, and `serving == false` answers `503` for 100% of requests. A
servlet that cannot check is not a servlet that skips checking.

Discovery order is part of that. `SessionStateVerifierProvider.load()` iterates
`ServiceLoader.stream()` and asks each `Provider` for its `type()` **before** calling `get()`: reading
the type defines the class without initialising it, so `DeploymentHygiene` can refuse a verifier whose
code sits in a world-writable place before that class's static initialisers — or its constructor — have
run. Checking after instantiation would be checking after the code had already executed. That ordering
leaves no trace in the return value — a candidate in a writable directory yields `null` whether it was
refused before it ran or after — so it is pinned by observation: the harness copies a probe verifier
whose static initialiser writes a marker file into two directories it controls, points `load()` at each
through a loader that defines the class from that directory, and asserts the marker exists for the
private one (the positive control — without it the second half passes on a probe that never loaded) and
never exists for the `0777` one. `SVC-hygiene-order` (reaching the class via `get().getClass()`
instead of `type()`) dies on exactly that assertion. Zero providers, two providers, a provider whose
code source cannot be inspected, and an empty `META-INF/services` entry all end identically: `503`,
never a guess.

Throttling, [`AttemptLimiter`](src/main/java/com/acme/portal/session/AttemptLimiter.java):

- **Per source and globally**, both checked, both in one monitor.
- **Refusals consume nothing.** A malformed or unverifiable assertion returns before the budget is
  touched, so an attacker cannot spend a victim's allowance with garbage. Verified over real HTTP by
  the `limited` mode: six free refusals stay `403`, and the grant count afterwards is exactly the
  configured allowance.
- **Global saturation is checked before the per-source counter increments**, so a flood that
  saturates the shared lane cannot lock out the clients that never sent it — the rule's "an attacker
  cannot use your own limit to lock a legitimate user out", applied to the global limit too.
- **The unknown-source bucket is smaller** (`max(1, perSource / 4)`), because "I could not establish
  your address" is the shape an attacker forges.
- **Canonicalisation is one-way, and its consequences are written down.** `::ffff:a.b.c.d` folds onto
  the IPv4 bucket — same host, one lane, no second allowance. The obsoleted IPv4-*compatible* form
  deliberately does not: folding that one is what used to turn `::1` into the bucket key
  `0.0.0.1/32`, an IPv6 peer asserting an IPv4 identity and sharing a lane with a machine it has
  nothing to do with. The consequence of refusing it is stated rather than left to chance: every
  address whose top 64 bits are zero — `::1` first — shares the single lane `0:0:0:0/64`. Those
  addresses are not reachable over a public link, so the lane holds local processes and port-forwarded
  sockets, and merging them can only ever delay a local caller; it cannot hand anyone a wider lane than
  their own address would have had.
- Bucket state is bounded (`PORTAL_HANDOFF_MAX_TRACKED_SOURCES`, default 200 000). When the map is
  full, a bounded reclaim hand walks at most 64 tracked entries looking for a bucket whose window has
  rolled; if it finds none the answer is `429`, not unbounded memory.
- **Every path through the limiter's monitor is O(1)**, refusal paths included. That is a security
  property, not a performance note: the monitor is shared by every request thread, so a loop whose
  length is set by how many sources happen to be tracked lets one attacker's flood make every other
  client wait behind it — the limiter turning into the lockout this rule exists to prevent. Measured
  here and printed by the suite: a new source arriving at a full map costs 7 µs, against 1 µs for an
  admission into an empty map — the version that scanned until it freed room cost 42 ms worst case for
  the same refusal. The harness pins the shape rather than the constant: it fills the map with 20 000
  distinct sources and then requires a refusal to stay both cheap in absolute terms and within 50x of an
  admission. `LIM-reclaim-bound` (sizing that walk by the size of the crowd) dies on the assertion.
- No account lockout exists here at all: this component has no account concept, and the limiter only
  delays retries.

### 4. Identifiers and tokens — CSPRNG, strict validation, documented residual risk, cookie attributes

- `SessionId.generate()`: 32 bytes from a shared `SecureRandom` → 43 unpadded base64url characters =
  256 bits. `getInstanceStrong()` is avoided deliberately (it can block a request thread); the shared
  instance is the platform-recommended pattern and reseeds from the OS source. Nobody inside this
  component calls it — the component the task describes receives an identifier that already exists, and
  issuing one for an asserted one would create a second session mechanism. It is there because rule 4
  says identifiers must be minted properly *somewhere*: a real session owner should call this rather
  than improvise, and the freshly minted value is fed back through `selfTest()` (shape, plus the
  diversity tripwire) so a CSPRNG or encoder that ever regresses throws instead of handing out an
  identifier no honest client can use.
- The externally provided identifier is validated as above and its residual risk is documented in
  both the javadoc and [the threat model](#threat-model-stated-plainly).
- Cookie attributes are invariants, not configuration:
  - `HttpOnly` and `Secure` are hard-coded `true` in `SessionCookiePolicy`; the settings loader has no
    path that sets them false (`POLICY-secure-hardcoded`, `POLICY-httpOnly-hardcoded` mutants).
  - `SameSite` accepts only `Strict` or `Lax`; **`None` is refused at construction** because it is
    meaningless without `Secure` and is the cross-site-leak setting. Set through
    `Cookie#setAttribute` because Servlet 6.0 has no SameSite setter (6.1 added one); Tomcat renders it.
  - Path must start with `/`, is charset-allowlisted and length-bounded; a `__Host-` name paired with
    any path other than `/` is refused at startup rather than producing a cookie the browser silently
    drops.
  - Cookie *name* is allowlisted, cannot start with a digit, cannot collide with a protocol keyword
    (`set-cookie`, `domain`, `expires`, …), and is length-bounded — the defaults are the safe ones.
  - No `Max-Age`/`Expires` ever ⇒ browser-session lifetime.
- 403/429/503 responses carry no `Set-Cookie` at all — asserted in-process and over HTTP.

### 5. Sensitive data: masked, bounded, private, and cleared from memory

- **Masked:** fingerprinting as in rule 2; the refusal page is a constant with no echoed input. The
  one string the granted page interpolates is the cookie *name* from validated configuration, and it
  goes through `ResponseBody.escapeHtml` anyway — output encoding should not depend on a validator
  never regressing. The escaper does one pass with `&` handled first, so no replacement can be escaped
  again by a later one; control characters including NUL become a space rather than an entity; and the
  limit is placed on the **escaped output**, not on the input read. Each character is charged the widest
  entity it could expand to (`&quot;`, six bytes) *before* it is appended, so the emitted page cannot
  pass 256 bytes however the characters fall, and an entity is always whole or absent — cutting on the
  output length instead would leave `&quo` in a document, which is worse markup than stopping one entity
  early. Bounding the input was the earlier defect: 256 `"` characters are 1 536 bytes of `&quot;`, on a
  page whose own guard had just reported itself satisfied.
- **Bounded stored size:** the only thing this component stores is rate-limit counters — one
  `{count, windowStart}` per canonical source key, at most `maxTrackedSources` keys, each canonical
  key at most 64 characters. No identifier, address or payload is ever retained past the request.
- **Private file modes:** the component writes no files. It additionally refuses to *start* if its
  own code source or the verifier's is world-writable (`DeploymentHygiene`, POSIX `OTHERS_WRITE`), and
  fails closed on a filesystem whose permissions it cannot judge — that is rule 8's "never load code
  from a shared place" enforced at runtime rather than left to a runbook. Two details in that guard are
  findings that were fixed rather than design flourishes. A code location the deployment names but that
  cannot be inspected — because it is not there — is now a **refusal** instead of a skipped entry: a
  check that certifies only the directories it happened to be able to `stat` has certified nothing about
  the ones it could not. And every path that reaches a refusal message goes through a sanitiser
  (control characters dropped, length capped, an empty name called out as unnamed), because those
  strings come from `java.class.path` and the filesystem — an unsanitised one puts a newline in a log
  line, which is how a file name forges a second record. Test scratch directories are created per PID
  and removed by a shutdown hook (not at the end of `main`, which the failure paths never reach).
- **"Clear credentials from memory when done" — the honest version.** The JVM cannot honour this for a
  `String`, and this task's input *is* a `String` handed over by another component. `String` is
  immutable, its value is not zeroable, garbage collection decides when the memory is reusable, and
  the JIT may intern or copy it. Pretending otherwise would be the kind of claim a reviewer is right
  to report. What the code actually does, and the most that is achievable here:
  - the fewest possible copies: `CacheSupport.digestHexPrefix` feeds the digest from the parts
    without materialising `prefix + secret`, and truncates during formatting rather than building a
    64-character digest string and cutting it;
  - every intermediate *it* allocates is zeroed on the way out (`byte[]`, `char[]`, digest output);
  - the copy it does not own is not extended: no cache holds it, no field outside the request-scoped
    `SessionId` does, and `value()` is package private so nothing else can retain it casually.
  A deployment that must bound credential lifetime at the byte level needs the platform's
  char[]-based APIs (`PBEKeySpec`, `SecretKeySpec`) on the *producer* side, which is the authenticator,
  not this component.

### 6. Failure behaviour — identical messages, comparable work, no permissive default

- **One** refusal body for `403`, `429` and `503`. The harness asserts every refusal path renders
  byte-identical output and that the set of distinct refusal bodies has exactly one member.
- **No existence oracle.** `403` means "no session was issued to you", which is true and already
  observable from the missing cookie; it never says whether the identifier was absent, malformed,
  unknown, or rejected by a broken verifier. The distinction *does* exist internally (`Outcome`) and
  goes only to the log, at `INFO`, as an enum name.
- **The response's shape says nothing either.** Same `Cache-Control: no-store, max-age=0`, same
  `Pragma`, same `Content-Type: text/html;charset=UTF-8`, same `X-Content-Type-Options: nosniff` on the
  grant and on every refusal, from one method (`applyStandardHeaders`) rather than four copies that can
  drift — drift here is the same leak as a differing body, reached without reading a byte. `HEAD` is
  answered through the *same* call path, minus the cookie: it declares the `Content-Length` the
  equivalent `GET` would have written, on the grant and on the `403`, `429` and `503` alike. A method
  whose responses have a different header set is a quieter oracle — "did I get a length back?" would
  tell a client that sent `HEAD` which gate answered — so the suite asserts the equality in both
  directions rather than trusting the sentence. A `HEAD` consumes the same rate-limit allowance as a
  `GET`: treating it as free probe room would make the cheapest request the one that asks whether a
  session exists.
- **Comparable work.** `WorkEqualizer.apply()` runs 160 chained SHA-256 compressions on **every**
  request, before the decision and on all five measured paths. Padding only the refusal paths is not
  enough: the `503` availability path short-circuits before them, and a path that costs nothing next to
  one that costs 87 µs is itself the "does this session exist" oracle. Measured in µs, copied from the
  `timing` section of `build/logs/harness.log` (in ms every path prints "1 ms", which is why the
  measurements are taken in nanoseconds; a few µs either way between runs on this box, so the gate is
  the ratio below and not any single one of these constants):

  ```
  granted              p50=84 us      no assertion         p50=87 us
  malformed assertion  p50=87 us      unknown session      p50=85 us
  not serving          p50=61 us      padding alone        p50=59 us
  spread=1.43x  equalizerCompressions=160
  ```

  The quantity the padding has to be sized against is the spread between *whole request paths*, not the
  cost of the decision inside them. Here the cheapest path (the availability refusal: padding plus a
  `503`) and the dearest (a refusal that also throttles, calls the store and writes a body) differ by
  roughly 25 µs of real work — the padding is inside both — so a padding of `P` leaves a spread of about
  `(P + 27) / (P + 2)`: staying under 2x needs `P ≳ 25 µs`, and 160 compressions (~59 µs) buys the
  margin — measured 1.43x. Two earlier values got this backwards in opposite directions and the suite
  reported both: 48 compressions (~18 µs) was sized against the 3–4.5 µs delta *inside* the decision,
  and produced an `17 µs` availability answer against `41–44 µs` everywhere else — a 2.59x spread, which
  is exactly the cheap-and-distinguishable path this class exists to remove; 200 compressions (~79 µs)
  was three times the work it hid and charged it to requests the throttle had already refused.

  Six assertions back this, because a ratio alone is not enough — a mutant that removes the work from
  *every* branch keeps the spread at 1.0 and would pass a spread-only check:

  - every outcome path costs at least 0.8x what `WorkEqualizer.apply()` costs when measured on its own
    **in the same run** (the floor is calibrated against the padding, not a hard-coded microsecond
    figure, because a fixed number is a property of the machine it was written on and would false-fail
    on hardware 20 % faster while tolerating quietly shrunken padding on hardware 20 % slower);
  - the padding is still real work (`≥ 5 µs`), which is what catches it being deleted or reduced to a
    token amount — the low backstop that a spread-only check cannot see;
  - the padding has not become the cheapest denial-of-service lever (`≤ 400 µs`). It is charged before
    every gate, including the throttle, so whoever can grow it buys server time with a packet. The
    count is a compile-time constant, so no request can grow it; this bound is for the maintainer who
    answers a timing complaint by turning the padding up until it is the most expensive thing a request
    does. 400 µs is about seven times the shipped cost, deliberately generous so a loaded box cannot
    false-fail here;
  - the five measured paths stay within 2x of each other (`spread < 2.0`), which is the bound the sizing
    above exists to satisfy — and the µs values are printed on every run so the ratio can be checked
    rather than trusted;
  - the two paths that must not be cheap relative to their neighbours are named individually: the
    availability refusal (`not serving ≥ granted × 0.5`) and the well-formed-but-unknown candidate
    (`unknown ≥ malformed × 0.5`).

  What no assertion can cover is a particular deployment's throughput budget, and the numbers for it are
  the ones printed above: 59 µs of padding is a ceiling of roughly 17 000 requests per second on one
  core doing nothing else, and the measured grant path (84 µs) works out near 12 000. That is the
  deliberate price of an answer whose timing says nothing, and it is written down as a trade in
  `WorkEqualizer` rather than presented as free — the accepted cost being that a request the throttle
  refuses still pays for the padding, so the limiter sheds the store round trip and the cookie write,
  not this.
- **Unknown input is rejected, never substituted.** Bad settings do not fall back to defaults — they
  stop the component. A non-`String` assertion attribute is "no assertion" rather than
  `toString()`-ed. An unparseable address is the shared restricted bucket rather than an anonymous
  unlimited one. A verifier that throws is "no". `SC_TOO_MANY_REQUESTS` does not exist in Servlet 6.0,
  so 429 is declared locally rather than approximated with 403.
- **Errors to the client stay generic; detail goes to the log.** No exception escapes this servlet —
  the container's error page would print class names, messages and stack, and `deploy/web.xml` routes
  `404`/`500`/`Throwable` to a static page with no request data regardless.

### 7. Concurrency — check-and-act is atomic

`AttemptLimiter.tryAcquire` reads the bucket, rolls it if stale, checks both ceilings, and increments
both counters inside a single `synchronized (monitor)` block. There is no window where two threads
can both observe `count == ceiling - 1` and both grant.

Ordering inside that block is a security property, not style: the global ceiling is checked *before*
the per-source increment (a saturated shared lane must not spend an innocent source's allowance), and
budget acquisition happens *before* the verifier call, so a slow store cannot be used to pile up
in-flight requests that all later pass.

`SessionHandoffService` is immutable after wiring, `ClientAddress` is immutable, `SessionId` is
immutable, and the one `ThreadLocal<MessageDigest>` is confined to `CacheSupport` and `reset()` in a
`finally`.

The servlet's four collaborator fields are `private transient volatile`, with `serving` written
**last** in both `configure` and `serveNothing`. That pairing is the whole point: a request thread that
observes `serving == true` has done an acquire read of the same field the wiring thread released, so it
must also see the three references written before it; a thread that observes `false` never reads them.
The container's promise that `init()` finished before `service()` ran is a spec sentence, not a
happens-before edge this class can lean on — without the volatiles a worker could pair `serving == true`
with a `null` collaborator, and the resulting NPE is caught and answered `503`. Nothing unsafe escapes
in that race, but it is a self-inflicted outage in the first requests after a deploy, which is exactly
when an operator is watching the endpoint. For a wire-once/read-many object rule 7's atomicity is
visibility, not locking, and this gets it without a monitor on the hot path.

The harness runs the limiter from concurrent threads against one bucket and asserts the total grants
equal the ceiling exactly — the assertion that dies first if the `synchronized` block is removed.

### Mutation battery: 44 mutants, 43 killed by a real assertion, 1 proven equivalent

`python3 -u tools/mutants.py --jobs 2 --max-jvms 2` — 314 s of wall clock on this box for the cycle
whose logs are on disk; a cycle run while I was also compiling in the foreground took 670 s.
The timing varies with what else is running, the verdict does not. Each mutant also prints its own
elapsed time, so a claim about how long one takes can be checked rather than believed:

```
SUMMARY mutants=44 seconds=314 slowest=LIM-reclaim-bound(73s) equivalent=1 killed(assert)=43
ACCOUNTED mutants=44 assertion-kills=43 build-failures=0 equivalent=1 needs-attention=0
```

Each mutant is one semantic edit to a frozen copy of `src/main` (the real sources are never touched;
`--dry` verifies every anchor matches exactly once before a cycle is spent). The tests are frozen
while a battery runs, so a mutant cannot be killed by editing the test that was supposed to catch it.
The per-mutant timeout defaults to 900 s — twelve times the slowest mutant measured here, which is a
limiter mutant because it rebuilds a 20 000-bucket map inside every timing pass — because the failure
mode it exists for is a hang, and a timeout that fires under someone else's load is worse than a slow
cycle: it would be reported as needing attention while the guard it was testing is fine. A timeout is
never counted as a kill.

Accounting is deliberately strict, because a green battery is worthless if a crash counts as a kill:

- `killed(assert)` — the harness printed at least one `FAILED` line. **All 43.**
- `killed(build)` — reported separately; a mutant that does not compile proves the edit was illegal,
  not that a guard is tested. **0 this cycle.**
- `harness-error` — exit ≠ 0 with no `FAILED` line, i.e. a crash. **0 this cycle.** Getting there took
  two real fixes: `SID-charset` used to crash the harness with `ArrayIndexOutOfBoundsException`, which
  was a genuine product fragility (now refused in `SessionId.inspect`), and the harness now wraps each
  section so an abort becomes a named failed check instead of an anonymous stack trace.
- `equivalent` — the edit cannot change any observable behaviour, so no honest assertion can kill it.
  One mutant is in that class (`ADDR-allowlist`), listed in the runner's `EQUIVALENT` table with the
  argument and the test that backs it, and the run prints it as its own status rather than counting it
  as a kill or hiding it. The table is self-policing: if a listed equivalent ever *does* die, the
  runner prints `NOTE … the two guards have diverged`, because the entry is then stale.
- Two earlier mutants were *equivalent by construction* and were replaced rather than reported:
  `SVC-null-verifier` renamed a private field (an NPE that the existing `catch (RuntimeException)`
  already treats as "no"), and `BODY-constant-refusal` renamed a constant. Both are now edits that
  weaken behaviour — an always-true verifier, and un-escaped HTML output.
- Survivors were **test gaps**, found and closed rather than accepted:
  - `SRV-not-serving` survived because deleting the guard turns the null collaborator into an
    exception, which the catch-all answers with the same `503` — the two guards are redundant and a
    status-code test cannot tell them apart. The gap is now observable two ways: the not-serving
    refusal must log **zero** SEVERE records (deleting the guard makes every request a logged server
    error — a false alarm and a log-volume amplifier), and an unwired servlet is built as a *never
    configured* object rather than by calling `configure(null, null, null)`, plus three new checks
    that any partial collaborator set leaves the servlet refusing. A `SRV-serve-partial` mutant
    (forcing `complete = true`) now dies on those.
  - The cycle that first ran the GET/HEAD response-shape checks produced two survivors, and each one
    named the cell that had no assertion: `SRV-head-length` (the checks existed on the grant path only,
    so a HEAD *refusal* could ship no `Content-Length` — "did I get a length back?" then separated
    refused from throttled without reading a body) and `SRV-shape-drift` (the `429` was checked for
    status, `Retry-After`, cookie absence and body, never for cache wording, so a throttle answering
    `public, max-age=60` passed every check). Both are assertion kills now — the first on
    `HEAD refusal declares the length its GET would have written`, the second on the throttle's wording
    compared to the grant from the same servlet.
  - `ADDR-allowlist` was killed in an earlier cycle by assertions that `InetAddress.getByName("fe80::1%9")`
    succeeds (so each numeric interface-scope id would be its own unlimited lane) and that
    `getByName("localhost")` resolves (so a hostname becomes a DNS query and a private bucket). Those
    assertions are still in the suite, and that is exactly how the mutant became equivalent: once the
    grammar was added, either layer alone satisfies them — the allowlist refuses `%` and non-hex letters,
    and so does the grammar — so no single-layer deletion can make them fail any more. What does fail
    when the grammar itself is weakened is the shape refusal (`ADDR-colon-grammar`) and the fold
    (`ADDR-compat-fold`). The relationship between the two layers therefore gets pinned by a sweep
    rather than by an outcome: the harness restates the allowlist independently and feeds both private
    grammar predicates 20 564 strings the allowlist refuses — every refused character alone and at every
    position of eleven address seeds, plus every short string mixing them with grammar characters — and
    asserts none reaches a bucket. Running the mutant, that section reports `failures=0`, i.e. the
    grammars refused all 20 564 too. Loosen a grammar later and the sweep fails, so the verdict expires
    on its own.
- **A green battery can be green for the wrong reason, and the summary line will not show it.** One
  cycle reported every mutant killed — `killed(assert)=44` of 44, including the mutant that is actually
  equivalent — while carrying a broken check of my own: the sweep's corpus-size floor was
  guessed at 30 000 when the corpus measures 20 564, so it failed on every run and each failure counted
  as a kill — including the one that "killed" the equivalent mutant. Detection came from reconciling the
  per-mutant logs rather than the tally: exactly one mutant had that `FAILED` line as its *only*
  failure, which is the signature of a broken test rather than a broken guard. Every threshold in the
  suite is now derived from a measured value, and the corpus floor states the number it was taken from.

Points raised in this pass that are **not** defects, recorded for the same reason as pass 1's:

- `0:0:0:0/64` (all-zero, not loopback) is a lane in which a mapped-format `::ffff:0.0.0.1` and a
  genuine `::1` share a throttle bucket. It needs the far rarer of the two spellings, it can only
  *shrink* a bucket against a neighbouring all-zero address, and refusing the all-zero address would
  cost the mapped fold its legitimate use.
- The padding runs **before** the throttle. Moving it after would save a throttled request the work —
  and turn "you are throttled" into a cheap probe, because the fast refusal would then be
  distinguishable from a grant by timing alone. The extra 59 µs of padding a refusal pays is the point.
- A HEAD request consumes handoff allowance exactly as a GET does. Allowing HEAD for free would make
  it a way to test whether a session is grantable without spending a grant, which is the outcome the
  throttle exists to prevent.
- `ADDR-allowlist` is the one mutant reported `equivalent` rather than killed. The character allowlist
  is a strict superset of what the two grammars accept — it admits only `[0-9A-Fa-f:.]`, which is
  exactly what dotted-quad and RFC 4291 need — so no string can exist that the loop refuses and the
  grammars accept. Manufacturing a kill would mean writing an assertion that fails for a reason
  unrelated to the mutant; the sweep turns that claim into a measurement with an expiry date.

## Known limitations

- Rule 4's residual risk (a fooled authenticator) is documented above and is not fixable here.
- "Clear credentials from memory" is bounded by what a JVM can do with an immutable `String`
  ([rule 5](#5-sensitive-data-masked-bounded-private-and-cleared-from-memory)).
- The rate limiter is per JVM. Behind N instances the effective allowance is N × the configured
  numbers; the global ceiling is a per-process circuit breaker, not a cluster-wide one. Sharing state
  would mean a cache, which means a new trust boundary and a new failure mode — deliberately out of
  scope for a cookie-writing component.
- `429` vs `403` is the one distinction kept between refusal families (availability vs
  authentication). Collapsing them would remove a signal an operator needs; the body and the headers
  are identical either way, so it discloses nothing about the session.
- No SameSite setter exists in Servlet 6.0 (`Cookie#setAttribute` is used and Tomcat 10.1 renders it),
  and `SC_TOO_MANY_REQUESTS` only arrives in 6.1 — hence local constants. Both are noted in the code
  where they matter.
